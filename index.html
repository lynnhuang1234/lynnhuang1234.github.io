Building a Customer Support Agent with RAG: Evaluation First, Autonomy Last

2026-10-08

Most "RAG chatbot" tutorials stop at retrieve, stuff the prompt, generate. Real customer support doesn't stop there. Some questions need documentation, some need business rules that move money, and some need a person. This post walks through how I designed one: a measured RAG service, wrapped as one node of a LangGraph agent. I focus on the decisions that turned out to matter, and the bugs that only showed up in live runs.

Code: github.com/lynnhuang1234/RAG_take_home

1. The problem

The setting is a campus food-ordering and smart pickup-locker service. Customers write in with three kinds of messages:

  • "How do I…?": how to order, how pickup codes work, what to do when a locker won't open. The answer is in a 67-entry FAQ.
  • "Where is my food?": a late order. The right response depends on the order's timings: chase it, add a small coupon, or refund it.
  • "I want my money back.": a refund request. Same inputs, a different rule table, and a question of who is responsible: the merchant, the delivery team or the platform.

The starting point was an existing MVP: one FastAPI file with a fine-tuned intent classifier, hard-coded refund and coupon rules, a similarity-threshold FAQ lookup, an in-memory chat history, and a cron job that filed a work order after two minutes of silence. It worked as a demo. It also promised refunds with no human check, lost every conversation on restart, and its FAQ answers had never been measured.

A pure RAG chatbot solves only the first kind of message. A pure "LLM agent with tools" lets a model decide who gets money. Neither is acceptable, so the design has two layers:

2. Requirements

I wrote these down before any code, because each one rules out a tempting shortcut.

Functional

  • Answer documentation questions with citations, and admit when the docs don't cover it.
  • Apply the reminder, refund and responsibility rules exactly as specified.
  • Hand off to a human when the order can't be found, the intent stays unclear, or something fails.
  • Support many conversations per customer, surviving restarts.

Non-functional

  • Money is never decided by a model. Coupons and refunds follow fixed rules and wait for an operator's approval.
  • Every quality change is measured before it ships.
  • Failures are recoverable: a timeout must not lose a work order or issue a coupon twice.
  • Auditable: for any reply, you can see which rule fired and why.
  • Privacy: phone numbers are personal data, so they're hashed in traces and in long-term memory.

Non-goals (just as important): real back-office integration (a mock keeps the old API contract), multi-language support, and letting the model take any action beyond read-only lookups.

3. Evaluation comes first

The single most useful decision in the project was treating every quality change as an experiment with a rule fixed in advance. Here's what that looked like and what it caught.

3.1 Build an eval set that can't leak

My first retrieval numbers looked great, and they were wrong. The best chunking strategy embeds each FAQ entry's question with its answer, and I was evaluating with those same questions. The retriever was matching queries against themselves.

The fix was a frozen, held-out set of 201 paraphrased queries (several per FAQ entry), generated once and never regenerated. Two consequences:

  • Paraphrases of the same entry are correlated, so confidence intervals use a bootstrap that resamples by source entry, not by query. Resampling queries treats near-duplicates as independent evidence and makes intervals too narrow.
  • Results on the old query set and the new one are never compared directly.

3.2 Pick metrics that don't move with the thing you're changing

Hit rate and recall@k sound natural, but they're computed per chunk, so changing the chunk size changes what they measure. For chunking work I used answer coverage@k, the fraction of the gold answer's characters present in the top k. I paired it with context characters@k as the cost side. A strategy that "wins" by stuffing more text into the prompt shows up immediately.

For generation, an LLM judge scores faithfulness (it extracts claims from the answer and checks each against the retrieved context) and answer relevance (a 1–5 rubric).

3.3 Check the judge before trusting it

An LLM judge is a model too. I had a second model label the same 40 calibration items with the same protocol:

Judgment Agreement
Claim supported Cohen's κ 0.77
Relevance (1–5) quadratic-weighted κ 0.86, 100% within one point

This shows the numbers don't hinge on one model's quirks. It does not show the judge agrees with people. That still needs human labels, and I say so wherever these numbers appear. Being explicit about what a validation does and doesn't prove is half its value.

3.4 Fix the ship rule before running anything

Each experiment had a primary metric, guardrail metrics and a small fixed set of candidates, all written down first. A change ships only if the primary metric's 95% interval excludes zero and no guardrail significantly regresses. Most ideas failed:

Change Outcome
Index each FAQ question with its answer, return the full answer Shipped. Coverage@5 0.375 → 0.654; relevance 0.753 → 0.819
Hybrid retrieval (BM25 + dense) Rejected. Coverage@5 0.654 → 0.575: keywords help exact matches and hurt paraphrases
Cross-encoder reranker Rejected. Quality change not significant; +394 ms to +3.3 s p95 latency on CPU
Citations Shipped. 92% of answers cite, 0% invalid citations, no quality change
Remove "contact a human agent" boilerplate from the prompt Shipped by product decision: faithfulness 0.828 → 0.983, but relevance −0.049, because answers the model declines now dead-end
Query rewriting for vague follow-ups Not shipped. It fixed a retrieval blind spot (4/11 → 11/11 on contact-info questions) but added ~1.7 s per turn

The table is worth more than any single result. Two popular techniques (hybrid search and reranking) didn't pay off on this data. Without a pre-registered rule, it's easy to talk yourself into shipping them anyway.

Cost discipline helped too. Eval runs use the Message Batches API (half price) and a response cache keyed by the exact request. The unchanged "before" side of an experiment is free to re-run, and an interrupted batch re-attaches instead of paying twice.

3.5 Evaluating the agent: different questions

The agent's rules are deterministic, so the first layer is plain testing: one test per graph branch, including boundaries (49/50/60/61/90/91 minutes), every responsibility combination, approval approve/reject, restarts, and crash recovery.

Tests prove the rules are wired correctly. They didn't find the most important bugs. Live end-to-end runs against the real model did, and each cost a few cents. I'll come back to those bugs below; the lesson is to budget for live runs, not just CI.

The open gap is a conversation-level eval: scripted multi-turn conversations scored on the final work order (right coupon, refund, responsibility and handoff?) plus a judge on reply quality. Unit tests can't replace it.

4. A workflow, not an autonomous agent

The biggest architecture decision: the agent is a LangGraph state machine where every business rule is a conditional edge, not a ReAct loop where the model chooses tools.

Routers are pure functions of the state; nodes do work but never choose the next branch. That buys three things that matter in support:

  • Auditability. Every turn's trace shows the path taken: refund → over_90 → refund_approve_coupon10 → delivery team responsible.
  • Testability. Each branch is a test with no model in the loop.
  • Predictable cost and latency. The LLM is called for exactly three jobs: classify intent when a small model isn't confident, answer documentation questions, and phrase the reply.

The intent step is a cascade: a small fine-tuned classifier, then an LLM if confidence is low, then one clarifying question, then a human. (The small model's training run is still pending, so today the LLM tier handles every turn: ~1–2 s and a fraction of a cent.) Asking before guessing is cheap; a wrong guess on a refund isn't.

When would I let a model choose tools? Only for read-only lookups (say, "has a rider picked up my order?") from an allow-list, scoped to the current customer. I built that path but left it off until an experiment shows it beats plain RAG. The next section shows why that caution was justified.

5. Let the model phrase; let code decide

Two live bugs shaped this rule more than any design principle.

Bug 1: the model dropped the money. The rules had decided a refund plus a 10-yuan coupon. The customer's message asked when the food would arrive. The model answered the timing question and never mentioned the refund or the coupon. Prompting harder isn't a fix. The fix is that the application appends a fixed sentence whenever a turn moves money ("We've submitted a refund request and a 10-yuan coupon for you"). The model writes the empathy; the code writes the commitment.

Bug 2: the model un-promised the money. With read-only tool calling turned on, a customer asked an unrelated question about the locker. The model looked up the order and helpfully "corrected" an earlier reply: "Correction: no coupon was issued." The coupon had just been submitted for approval. That contradicts a business commitment, and no unit test would have caught it. The fix has two parts:

  1. The tool model's prompt forbids revisiting earlier replies or mentioning money.
  2. A deterministic guardrail discards any tool-model answer that mentions refunds or coupons and falls back to the plain RAG answer.

Prompts reduce how often this happens; only the guardrail stops it.

Everything else follows the same principle:

  • Money waits for a person. The graph pauses on LangGraph's interrupt() and resumes when an operator approves. The customer is told the request was submitted, not done.
  • Tools run through a manifest, enforced by one executor rather than by convention. Each tool declares its risk, whether it needs approval, whether it's safe to retry, and whether the model may see it. A money tool without approval refuses to run, and only read tools can be model-visible. A new tool can't skip the checks because it can't be registered without a manifest entry.
MANIFEST = {
    "order_status":  ToolManifest("read",  requires_approval=False, idempotent=True, retries=2, model_visible=True),
    "issue_coupon":  ToolManifest("money", requires_approval=True,  idempotent=True, retries=2),
    "submit_refund": ToolManifest("money", requires_approval=True,  idempotent=True, retries=2),
}

6. Memory: facts are fetched, never remembered

"Agent memory" often means "store everything and retrieve it later". In support that's dangerous, because business facts go stale. The order the customer confirmed at minute 40 is a different case at minute 95. So the rule is:

  • Short-term memory is the checkpointed conversation state. The order is re-fetched just before every rule decision. If the latest order has changed (the customer placed a new one), the conversation goes to a human instead of deciding on the wrong order. Long conversations fold older turns into a rolling summary, which never carries money decisions. Those live in the work order.
  • Each consumer gets its own view. The small classifier sees only the latest message; the LLM classifier sees it with two earlier messages as context; the reply model sees the summary plus recent turns. An earlier version fed the last three messages to the classifier, so an earlier "refund me" outvoted a new how-to question and the customer was told "I don't have permission to help with that." Again, found in a live run.
  • Long-term memory is a small per-customer profile: refunds and coupons actually applied, past handoffs, and a few short notes ("locker at dorm 3 often fails"). It's keyed by a keyed hash of the phone, expires after 180 days, can be deleted on request, and is written after the conversation ends, never on the request path. Its most valuable use isn't personalisation: approvers see "2 compensations in the last 30 days" when deciding on a third. The notes come from customer text, so they're a prompt-injection surface: they are bounded, fenced and labelled as background, and the rules and tools never see them.

7. Failures are state, not log lines

The MVP's failure handling was logger.warning(...). A work order that failed to file was simply gone. The production version treats every failure as something recorded in the conversation state and repaired:

  • Idempotency keys on every write. A coupon call that times out after the back office applied it is retried with the same key, and the back office applies each key once. No double coupons.
  • An outbox for money. After approval, the intended actions are written to the checkpointed state before any of them runs. If the process dies between the coupon and the refund, a background job resumes the run from the checkpoint. The keys make re-running the coupon a no-op. (This is a test: crash after the coupon, resume, assert exactly one coupon.)
  • Partial failure goes to a person with specifics. If the refund fails after retries but the coupon succeeded, the human gets failed_actions: ["submit_refund"], not "something went wrong".
  • A background job refiles work orders the back office rejected, with an attempt limit and a metric to alert on when it gives up.

Underneath sits the usual LLM resilience: retries with jitter, a circuit breaker, a server-side fallback model for refusals, and 503 + Retry-After instead of a thread sleeping through a long rate-limit wait.

8. What I'd do next

  • A conversation-level eval for the agent (above). It's the biggest gap.
  • The tool-calling experiment: tool model vs plain RAG on how-to and order-status questions, judged on relevance and faithfulness to tool results, with latency and cost as guardrails.
  • Authenticated identity. Today the API trusts the phone number in the request, so the customer API key must stay on a trusted backend. The fix is a signed user token.
  • Human calibration of the LLM judge, plus Postgres-backed state for horizontal scaling.

Takeaways

  1. Evaluation is the product. Most ideas, including popular ones, didn't survive a pre-registered rule. Leakage-free eval sets and the right metric matter more than the retriever.
  2. Use a workflow where the business has rules. Save autonomy for read-only lookups, and ship that only after it's measured.
  3. Let the model phrase; let code decide. Commitments to customers (money, promises) come from the application, and a guardrail beats a stronger prompt.
  4. Facts are fetched, never remembered. Memory should hold what happened, not what is.
  5. Live runs find the real bugs. All three serious bugs in this project (a lost refund, a contradicted coupon, a misclassified question) passed unit tests and were caught for a few cents of API calls.
